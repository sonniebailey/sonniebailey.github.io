# Technical notes

How the site is built, for whoever maintains it. readme.md covers day-to-day editing; this covers the machinery.

## Stack

- Python 3.12 build script: Jinja2 templates, python-markdown (extensions extra and smarty), PyYAML for page settings. Pinned in requirements.txt.
- Output is plain HTML, CSS and four small vanilla JavaScript files. No framework, no bundler.
- Hosted on GitHub Pages. A GitHub Actions workflow (.github/workflows/pages.yml) builds and publishes the site on every push to main.
- Pillow is used only by utils/optimise_images.py, not by the build.

## Folder layout

- content/ - one markdown file per page, plus site.json, plus content/snippets/ for wording shown inside templates rather than as a page (capacity.md, the Limited capacity popup)
- templates/ - Jinja2 templates: base.html (page shell and head), page.html, home.html, faq.html, partials/header.html, partials/footer.html, partials/capacity_dialog.html (the Limited capacity sticker and its popup), partials/hero_bg.html, partials/logo.html, partials/icons.html (home.html no longer uses it)
- css/ - main.css imports variables.css, base.css, prose.css, components.css, responsive.css in that order
- js/ - header.js (floating header state), menu.js (mobile menu), reveal.js (scroll-in animation), faq.js (expand/collapse all), dialog.js (opens and closes popups)
- images/ - images as published; the build copies this folder unchanged. There is no logo file: site.json sets no logo and the header shows the wordmark
- originals/ - full-size source photographs kept for re-cropping or re-sizing; never published. Holds hero-lake.jpg (7008px, about 19MB), the original of the page photograph; og-image.png, the screenshot the share image was saved from; and sonnie.psd, the Photoshop source of the portrait images/sonnie.png.
- icons/ - the brand icon, following devkit's icons convention. master.svg is the source: a gold seedling that hides a lower case f, on a gradient from a touch lighter than --brand-primary to darker than --brand-primary-dark, full bleed, with the plant inside the central 80% so maskable Android icons do not crop it. generate_variants.py (copied from devkit) renders favicon.svg, favicon.ico, apple-touch-icon.png, icon-192.png and icon-512.png from it; run it with --targets web-favicon, because its default set also rewrites og-image.png as a plain icon card. og-image.jpg (1200 x 630, JPEG quality 85, about 56 KB) is the share image, which site.json social_image points at: the gold seedling beside "Fairhaven" over a gold "Wealth", on the lake photo under a navy wash. Neither the build nor the generator makes it; it was drawn as option D in artifact/share-image-mockups.html, screenshotted and saved as JPEG (the PNG screenshot, kept in originals/, was about 600 KB), so a change to the photo, icon or name means redrawing it there; site.webmanifest names the two PNGs. icon-print.svg and icon-print-reversed.svg are black and white hairline versions of the same mark for print, reference only. The build copies the folder, also copies favicon.ico to the site root so browsers' blind requests for /favicon.ico are answered, and base.html links the icons/ favicon files and the manifest. Future Friends uses the same mark with a navy echo behind it; the two were designed together in lookbook's artifact/fairhaven-ff-pairs.html
- build.py and build/ - the build; build/orchestrator.py runs the steps in order
- preview.py - build then serve _site/ locally
- settings.py and settings.html - local editor for site.json and the brand block; never published
- utils/optimise_images.py - photo resizer
- tests/ - pytest tests for the build modules
- .github/workflows/pages.yml - builds and publishes the site on every push to main
- disclosure.pdf and privacy.pdf - the disclosure statement and privacy policy, linked from the footer via footer_links in content/site.json. Any PDF at the repo root is copied to the site root, so its address (eg /disclosure.pdf) matches the old site's and stays fixed for anything linking to it
- _site/ - build output, ignored by git, recreated on every build

## Build steps

build/orchestrator.py run_build, in order:

1. site_config.load_site_config reads content/site.json and checks every required key (name, tagline, domain, phone.display, phone.tel, email, address.lines, address.single_line, hours, nav, favicon, social_image, fonts.heading, fonts.body, fonts.google_css; logo is optional; map is optional and, if present, needs embed_url and link_url; footer_links is optional and, if present, is a list whose items each need label and href).
2. page_loader.load_pages reads every content/*.md, splits the YAML front matter, checks title, description and layout (page, home or faq), applies defaults (hero_image images/hero.jpg, noindex false, show_map false), checks the hero image exists, checks the shape of cta and features and that intro is text, and derives the URL from the file name. The glob is not recursive, so content/snippets/ is never read as pages.
3. output.prepare_output empties _site/ (retrying briefly if a sync client such as Dropbox holds a lock).
4. snippet_loader.load_snippets renders each content/snippets/*.md (no front matter; the first H1 becomes its title) through markdown_render.render_body and sets the result as the Jinja global snippets, keyed by file stem.
5. For each page: markdown_render.render_body lifts the first H1 out as the page title (hero_title) and renders the rest to HTML; faq_transform.to_details wraps each H2 section in a details.faq-item (answer inside a div.faq-answer; a heading with nothing under it becomes a plain div.faq-item--static with no toggle), collected into a single div.faq-list, for faq pages; page_renderer.render_page renders the template named after the layout; root_relative.rootify rewrites 404.html's links to start with / so it works from any path.
6. output.copy_assets copies css/, js/, images/ and any repo-root *.pdf.
7. sitemap_writer writes sitemap.xml (every page except 404 and noindex pages) and robots.txt.
8. checks.check_output reads the output back and fails the build if any page is missing its header, footer or main, still contains template syntax, links to a css/js/image file that does not exist, has the wrong number of current-page markers, or if 404.html, sitemap.xml or robots.txt is missing.

Any problem raises BuildError with the file and field named, build.py prints it and exits 1. There are no fallbacks: a broken page is never published.

## Template context

Every template receives: site (the site.json object), page (title, description, url, canonical, hero_image, cta, intro, features, noindex, show_map, layout), hero_title, content (rendered body HTML), build (year), and the global snippets (snippets.<stem>.title and snippets.<stem>.html). Templates run with StrictUndefined, so referring to a value that does not exist fails the build rather than rendering blank.

The header shows site.name as a text wordmark in the heading font, kept discreet: one size step above the nav links (--font-size-wordmark) and slightly faded (--wordmark-opacity). Setting logo in site.json to an image path swaps in that image instead. The wordmark is the default because a bitmap logo cannot recolour for dark mode, so it has to be legible on both a light and a dark header or shipped twice; a business with a real logo should supply an SVG that inherits currentColor.

The header marks the current page by comparing page.url with each nav item's href, adding class is-current and aria-current on the desktop nav and again on the mobile menu. The mobile menu also opens with a Home link (hard-coded in partials/header.html, not from site.nav), because the open menu covers the header's home button; on the home page it and the home button are the two markers checks.py expects. The menu's close button shares the popup's round gold face and hover (.dialog__close, .menu-close in components.css). At the bottom of the open menu, under the phone number, email and footer links (one per line), one row (.mobile-menu__contact, items aligned to the row's bottom edge so the email icon sits level with the bottom of the call button) holds a plain white email icon (a mailto: link, .call-button--plain, gold on hover) flush left and a large round gold call button (a tel: link, .call-button--large, --call-button-size-large, --call-icon-size-large) on the right, with a soft gold glow (--call-button-size, --call-icon-size, --call-button-glow, --call-button-glow-hover).

## Head and SEO

base.html sets the title (site name and tagline on the home page, page title and site name elsewhere), meta description, canonical link built from site.json domain, Open Graph tags with site.json social_image as the default image, a Twitter card tag, a JSON-LD FinancialService block (name, url, telephone, email, image and address locality, all filled from site.json so it cannot drift from the visible contact details), the favicon links (site.json favicon, icons/favicon.svg, the apple-touch-icon and the web manifest), the Google Fonts stylesheet from site.json fonts.google_css and css/main.css. A page with noindex true also gets a robots noindex meta tag and is left out of the sitemap.

Every page also loads the Plausible visitor-counting script (the outbound-links variant, data-domain fairhavenwealth.co.nz), carried over unchanged from the previous site so visitor numbers continue across the switch. It is hard-coded in base.html, not a site.json setting. Plausible ignores localhost, so previews are not counted. No integrity hash is set: Plausible updates the script in place, and a pinned hash would silently stop counting when it changes.

Search visibility is a whole-site setting, separate from the per-page noindex flag. site.json search_visible is optional and defaults to false, applied by site_config.load_site_config so the value is always present downstream. False puts `<meta name="robots" content="noindex, nofollow">` in every page head and makes sitemap_writer.write_robots emit a `Disallow: /` robots.txt with no Sitemap line; true restores the allow-all robots.txt naming the sitemap, and the per-page noindex flag applies as before. The sitemap itself is written either way, so the post-build check for its presence needs no special case. The orchestrator logs which state every build is in, in both directions, so the state is readable in the GitHub Actions build log.

The default is false rather than true because the two mistakes are not equal: a forgotten key leaves a finished site unlisted, which one commit fixes, whereas the reverse would put a client's unfinished draft in front of Google. A new site is therefore hidden from its first build, and going live is a single deliberate edit. Treat that edit as one-way: once a site is live, deploying a hidden build would remove it from search results.

## CSS

css/variables.css is the only file that contains literal colours, sizes and font names. Everything else references them as var(--token). The BRAND block at the top holds the eight values a new site changes (primary, primary dark, accent, background, text, heading font, body font, corner radius); all other tokens derive from those, mostly through color-mix, so changing the brand moves the tints, scrims, shadows and dark palette with it. Breakpoint numbers in responsive.css are the one exception, because media queries cannot use variables.

Derived tokens are grouped by what they are for: a four-step brand tint ramp for hovers, rules and fills; surface colours where raised surfaces are translucent rather than solid, so the page shows through and cards brighten on hover; brand-tinted shadows, because flat black shadows read as grey smudges on a warm background; motion tokens (easing curves and durations); per-area rhythm tokens (section, card, feature gap, content inset) that responsive.css restages at each breakpoint; and a type scale with semantic prose tiers layered on top, so components reference the tier rather than a raw size.

A derivation is a default, not a constraint. Where a particular brand needs a hand-tuned value, overwrite the derived token directly; nothing depends on it having been computed.

The layers have distinct jobs and rules do not cross between them. base.css owns the reset, the heading system and the page furniture (header, footer, page heading). prose.css owns running text inside main: the vertical rhythm between blocks, lists, quotes, rules, tables, code and captions. components.css owns discrete components (nav, wordmark, cards, FAQ, theme toggle, map). responsive.css restages tokens at each breakpoint.

Spacing between a page's main blocks has one owner. main > .container in base.css is a grid whose gap is --section-gap, with --section-gap as its padding at both top and bottom, so the space under the header matches the space above the footer on every page; the footer's own padding (--header-inset, the same space the header leaves above and below its logo) closes the page. The footer paints its own background, so the join is a visible colour boundary, and padding added inside the footer sits below that line: it separates the footer's text from the boundary but does nothing to stop the page's last block touching the edge of its own section. --section-padding-block is still defined and stepped down in responsive.css but no rule uses it. The blocks it lays out (.prose, .features, .faq-page, .map-embed) carry no vertical padding or margin of their own, so a new block added to a template is spaced correctly without being told to be. This replaced an arrangement where each block padded both its top and its bottom with a full --section-padding-block, which rendered a doubled gap at every join between two of them: text to feature cards, text to map, map to footer, and text to footer on a page with no map. The rule is scoped to main because the header and footer share the .container class and keep owning their own padding. main > .container > * sets min-width: 0, since a grid item does not shrink below its content by default and a wide table or code block in .prose would otherwise stretch the page.

Type is defined by role, not by level. variables.css holds the raw scale, then names tiers on top of it (--font-size-heading-section, -sub, -minor, -card for headings; --font-size-lead, -prose, -secondary, -caption for running text). A page's opening paragraph is set like any other; --font-size-lead is now used only by quotes. base.css maps each heading level to a tier once; everything else references the tier. responsive.css steps the tiers down together at each breakpoint, so the intervals between levels stay proportional rather than the largest heading collapsing onto the others.

Font weights are tokens (--weight-body, -medium, -semibold, -heading) and only weights actually listed in the Google Fonts URL in site.json may be given values. Asking for a weight that was not loaded makes the browser synthesise a fake bold, which is a common and hard-to-place cause of type looking inconsistent from one component to the next. Changing the fonts means checking the weights in that URL against these four tokens.

Vertical rhythm is tokenised as --flow-gap (between paragraphs), --flow-gap-heading-top and -top-minor (above a heading), --flow-gap-heading-bottom (below one) and --flow-gap-block (around quotes, images, tables). The asymmetry is deliberate: a heading is given more space above than below so it binds to the text it introduces. Equal margins are what make a page read as evenly but arbitrarily spaced.

prose.css works off elements alone, never classes, because an author writing markdown cannot add one. Every element markdown can emit is styled, including ones a brochure site is unlikely to use (code, tables), since an unstyled element falls back to browser defaults that visibly do not belong to the rest of the page.

--ground-texture paints a texture on the header and footer bars only, via header::before and footer::before, so the bars read as a material rather than flat colour. The page itself is not textured. It is Snoopy's 45-degree fabric weave tile, copied into images/ in both tones the pattern ships in, drawn at native size and repeated. Set it to none to switch it off. Beneath the texture, header and footer carry a barely-there gold wash (--bar-gold-wash, the brand accent at 4%) over a black wash (--bar-black-wash, black at 75%), both as background-image layers over their background-color, so the bars sit darker with a slight warm cast.

The page photograph is set by templates/partials/hero_bg.html as two background-image declarations: a plain JPG, then an image-set() offering the WebP of the same name first and the JPG second, so browsers without image-set() keep the JPG. The WebP path is derived by swapping .jpg for .webp. Debt: the build checks only that the JPG exists, so a missing WebP builds cleanly and shows no photograph in modern browsers. The photograph files are 2560px wide (hero-lake-2560.jpg and .webp); the 7008px original is kept in originals/hero-lake.jpg, outside the folders the build publishes.

Page changes are ordinary page loads with no transition. A full-width hero banner and a page-drop transition between pages were removed; some names still carry the word hero (the hero_image and hero_title template values, the .hero__cta button class, --measure-hero and partials/hero_bg.html), though they now serve the page backdrop, the page heading and the cta button.

settings.py edits only the lines between the BRAND markers, so keep one token per line in the form `--name: value;`. Everything added below the markers is invisible to it.

## Trial layout

The layout below began as a trial and is the decided layout: pinned footer (hidden on phones), home page without feature cards, the Limited capacity sticker (oblong: rounded rectangle, stitched edge, slight tilt) and its popup, and a photograph behind every page. What is in place:

- Page backdrop. base.html renders the page's hero_image as div.page-backdrop, fixed to the viewport behind everything (z-index -2). Its ::after lays --backdrop-dim and --backdrop-blur over the whole photograph, so text can sit straight on it.
- Page heading. Each page template opens its container with .page-heading (PAGE HEADING in base.css): the h1 (hero_title) with the optional intro line under it (.page-heading__text; the intro on page and faq layouts only), and the cta on page and faq layouts, top-aligned so it sits level with the first line of the title. The capacity sticker appears in this row on the home page only.
- Home page. home.html stacks the heading, the prose and the Limited capacity sticker down a left-aligned column (.container--centred), vertically centred between header and footer by a min-height calculated from --header-offset and --footer-height. The heading row carries the gold seedling (icons/seedling.svg, the same image as the header home button, img.page-heading__mark, --heading-mark-size 4.5rem) at its right end, vertically centred against the two-line heading; .container--centred .page-heading is stretched back to full width because the column's justify-items start shrink-wraps its children, so the mark's right edge lines up with the paragraphs below. At 480px and under the mark is hidden, since stacked under the heading it read as an orphan. The sticker is the home page's main button: there is no cta button on the page itself. The cta link (index.md's cta) sits at the bottom of the popup instead (.dialog__cta, rendered only when page.layout is home), so visitors reach About through the Limited capacity message. A visitor without JavaScript never sees the sticker, so home.html also renders the cta link inside a noscript element where the sticker sits. Both cta links are drawn larger than on other pages (.container--centred .hero__cta), the popup's included, because the dialog markup sits inside the home container. Its container has no padding of its own, so on a screen too short for the block the text would sit against the header and footer. The feature cards (features in frontmatter, partials/icons.html, .features in css) are not rendered and content/index.md no longer defines any; the loader still validates a features field if a page has one.
- Footer. partials/footer.html is the site's only footer and contact section: footer_note and footer_links stacked one per line on the left, and hours, email and phone stacked one per line on the right, both top-aligned, padded top and bottom by --header-inset to match the header, and fixed to the bottom of the viewport with the scrolled header's surface, blur and fabric texture. There is no address or copyright line. body is padded at the bottom by --footer-height so the footer never covers the end of the page. --footer-height is a declared value, not a measured one; where its content grows taller than that height allows, the footer can cover the last of the page. At 480px and under the footer is hidden (it stays in the markup because checks.py requires a footer) and --footer-height drops to 0; its contents are repeated in .mobile-menu__footer at the bottom of the mobile menu (partials/header.html), so a change to the footer's fields needs making in both partials. The spacing paragraph under CSS above still describes the footer as painting a visible colour boundary; that no longer applies while the footer is fixed.
- Capacity sticker. partials/capacity_dialog.html holds the Limited capacity button and its native dialog, included by home.html only, under the home page text; page and faq layouts do not include it, so About, Testimonials and the 404 page show no sticker. .page-heading__text takes flex 1 1 0 with min-width 0, so a page intro line wraps beside a cta button instead of pushing it below the heading. At 480px and under the heading row stacks instead. The button is a gold oblong sticker with rounded corners (--badge-radius), a dashed stitched edge, and a slight tilt (--badge-tilt, applied with the rotate property so the shared hover scale adds to it); its text sits on one line and sets its width, with --badge-font-size stepping down at 768px and 480px (--sticker-sheen, --sticker-shade) styled in components.css under DIALOG. The dialog uses the header's frosted surface, capped at --dialog-width (set so its text runs the same width as a page's text column), with the gold border and glow the FAQ panels take on hover (--hover-gold-border, --hover-gold-glow). Behind it the page is dimmed by --dialog-backdrop and blurred by --dialog-backdrop-blur. A smaller copy of the sticker (.dialog__sticker), at the same tilt as the page button, sits across the middle of the dialog's top edge, half outside it; at 480px and under it moves to the left, lined up with the text (--dialog-sticker-left, --dialog-sticker-shift). It stands in for a heading: the popup has no visible heading, and the dialog is named for screen readers by an aria-label taken from the snippet's title, while the sticker copy is hidden from them. Because the sticker hangs past the edge, .dialog--stickered turns off the dialog's own clipping and scrolling moves onto .dialog__body. The close button is a round gold button (--dialog-close-size, 40px at 480px and under) hanging over the top-right corner (--dialog-close-offset), positioned against the dialog rather than the body so it stays put while the text scrolls and, sitting mostly outside, never covers the text. The body's padding is --dialog-padding, cut from 2.5rem to 1rem at 480px and under so the text keeps a usable width, with extra at the top (--dialog-padding-top, larger at 480px and under where the sticker sits over the text's left edge) so the first line clears the sticker. Its text size is --dialog-font-size, one step smaller at 480px and under. On the home page the popup's cta link is drawn at the ordinary button size (.container--centred .dialog__cta), overriding the home page's larger one. Its wording, and its aria-label, come from content/snippets/capacity.md via snippets.capacity; the sticker labels on the button and the top-edge copy are still fixed text in the partial.

## Single page

Decided design, not yet built. Until the work tracked in status.md lands, the rest of this document describes the site as it is on disk, and where this section and another disagree the other is current.

The site is one document. Home, About and Testimonials are panes in a horizontal row, one screen wide each, and the visitor moves between them by sliding the row sideways rather than loading a new page. The window itself never scrolls: each pane scrolls up and down inside itself, so a long pane such as About keeps its own scroll position while the visitor is on another pane. The header and footer stay fixed as now. This replaced the one-file-per-page build and the cross-document page-drop transition outright; there is no multi-page mode to switch back to. On phones the browser's address bar does not collapse on scroll, because the window itself never scrolls, so the panes have slightly less height than a scrolling page would.

Pane order is Home first, then the nav items in site.json order, so adding a page is still a markdown file plus a nav entry and the row takes any number of panes. The row is a loop: a slide always takes the short way round, and where the two ways are equal (an even count) it goes right. With the current three panes every pane is one step away in each direction: from About, Testimonials is to the right and Home is to the left; from Testimonials, Home is to the right and About is to the left. The loop rules out the browser's native scroll-snap, which cannot wrap, so the slide is JavaScript moving the row. Under reduced motion the panes swap with no slide.

Each pane keeps its own heading row, as the separate pages had; the sticker and its dialog would be the home pane's alone, since a document cannot hold three elements with the same id. The faq layout's expand-all control is scoped to its own pane. The backdrop photograph is index.md's hero_image, since one document has one backdrop.

Addresses. The build writes the same document once per pane, as index.html, about.html and testimonials.html. Each copy carries its own title and description and is marked at build time with which pane is current, and CSS positions the row from that mark alone, so each copy opens on its own pane without a slide and without JavaScript. Nav links are ordinary links to those files; JavaScript intercepts them to slide instead. A visitor without JavaScript therefore moves between panes by page loads and sees the whole site. Existing and shared links behave as before and no redirects are needed.

Every slide, whether from a nav click, a swipe or an arrow key, pushes a history entry, changes the address to that pane's file and sets the tab title to that pane's title, so the browser's back and forward buttons replay the slides. The address, not localStorage, is the only carrier of which pane is current, and nothing is stored on the visitor's device.

Every copy's canonical link points at index.html, so search engines index one page under the home address, and that page holds all three panes' text. The copies are near-identical, so they would be folded into one either way; naming the home page makes the choice explicit, at the cost that About and Testimonials never rank under their own titles. The other two copies are indexable, not noindex; a noindex copy cannot pass its weight to the canonical one. The sitemap lists index.html only. The off-screen panes' text is in the document on every copy, as the FAQ answers already are inside closed details elements, so one indexed page carries the whole site's text. Page weight is unchanged in substance: the text of all three panes is a fraction of the one photograph every page already loads, and the About portrait is lazy-loaded so it costs nothing until that pane is seen. The 404 page stays a separate document.

Input. A visitor slides between panes by clicking a nav item, by swiping left or right on a touch screen, or with the left and right arrow keys. The swipe handler has to tell a sideways swipe from a vertical scroll inside a pane, and arrow keys are ignored while the dialog or mobile menu is open or focus is in a form field. Panes not on screen are inert, so keyboard focus and screen readers cannot reach them, and focus moves to the new pane after a slide.

## Dark only

The site is dark and offers no alternative. base.html hard-codes data-theme="dark" on the html element, so the [data-theme="dark"] block in variables.css always applies. There is no toggle, no preload script and no theme.js; the sun/moon button and its styling were removed along with them.

The :root block above the dark block is retained as the base layer the dark values override, not as a theme anyone can reach. Only colour tokens are redefined; spacing, type and motion come from :root. Stripping the light values entirely is possible but has not been done, on the grounds that it is a larger edit for no behavioural gain.

The dark surfaces are Snoopy's values copied verbatim (snoopy/css/variables.css) rather than derived from the brand colour: ground #060608, header #1B1B1F, panels as faint white over them, link #7FA6CE. The point is that this site and that app read as the same dark, which a derivation cannot guarantee. The header and footer texture is Snoopy's 45-degree fabric tile, drawn at native size and repeated. One deliberate departure: the FAQ panels (.faq-item, used on FAQ, About and Testimonials) do not use Snoopy's faint-white --colour-card but their own --panel-bg and --panel-bg-open, translucent black at 35% and 45%, so they sit darker than the page rather than lighter. --colour-card still styles the feature cards, which are not currently rendered.

Links inside running text (.prose a, prose.css) are gold with a faint gold underline at rest that goes solid on hover (--colour-link-prose, --link-underline, set in the dark block). The general link colour, --colour-link, is white in the dark block, the same as body text, so without these running-text links read as plain text; the base underline tint is navy and barely shows on the dark ground. Navigation, buttons and the logo style their own links and are unaffected.

The consequence to keep in mind is that changing the BRAND block no longer moves the dark palette with it. A brand change means revisiting these values by hand.

## Header

The header is fixed and floats over the page photograph. main is padded at the top by --header-offset to clear it, and the container's own --section-gap supplies the space below the header. --header-offset is currently set to --header-height alone, since no banner is shown; add --banner-height back if the banner returns.

The header is frosted at all times: a translucent fill over a backdrop-filter blur. The blur must be on the base rule rather than only on the scrolled state, because behind plain content the backdrop is a near-flat near-black page and blurring a flat colour is indistinguishable from not blurring it. The photograph is the only backdrop with structure to soften.

js/header.js adds .is-scrolled once the page scrolls at all, switching the fill from a faint tint to the heavier surface, since running text has to stay legible passing underneath. The header casts --shadow-header down onto the page in both states, and the footer casts --shadow-footer up, so both bars stand apart from the body. These are near-black (--bar-shadow-colour) rather than brand-tinted, since a tinted shadow barely shows on the dark page. Before scrolling every item in the header is forced to --colour-text-on-dark (header:not(.is-scrolled) in base.css), a holdover from when the header sat over a lighter hero photograph; on the dark-only site it changes nothing visible. The burger's bars use --colour-text-on-dark in every state (components.css), never --brand-primary, which is a slate blue.

site.json's optional banner key renders a notice row inside the header, under the nav row. It is currently null, so no row shows. It paints no fill of its own; the header's frosted surface covers both rows, so the two cannot stack up two layers of tint. --banner-height is a declared value restaged in responsive.css, not a measured one, because the notice wraps at narrow widths.

The current page is marked in the nav by blurring its patch of the header further than the header already does, plus --hover-gold-glow (the gold hairline border and halo the FAQ panels take on hover); hover takes the same glow with half the extra blur, so blur is the only thing telling hover and current apart. There is no underline and no colour change. At rest the page buttons (home button and nav links, not the phone number) carry a faint 1px outline, --nav-rest-glow (the brand gold at 22%, well under the 55% hover border, plus a 12px gold halo at 8%), which hover and current replace with the full gold border and glow. Blur only stacks downward -- a child's backdrop is the parent's already-filtered result -- so a nav item can add blur but cannot reduce it below the header's. Every nav link carries the pill's padding and radius with a transparent fill, cancelled by an equal negative margin, so the items neither move nor cost extra space when a state paints. --nav-gap is wider than --header-gap because it has to clear two pill insets and still leave visible air between neighbours.

A home button sits left of the wordmark: the gold seedling from the brand icon with no background (icons/seedling.svg, hand-copied from master.svg's gold paths, so a change to the icon means updating it too; img in partials/header.html, class .nav-home) in the same pill, sharing the nav links' hover and current-page rules. It is marked current, with aria-current, on index.html only. It sits outside both nav blocks; the mobile menu has its own Home link, so checks.check_output expects 2 current-page markers on index (the home button and the menu Home link) and 0 or 2 on every other page. The wordmark beside it is still a link home but takes no pill.

The gold hover look is painted with three tokens derived from --brand-accent: --hover-gold-fill (a faint tinted fill), --hover-gold-border (a hairline accent border) and --hover-gold-glow (an accent ring plus feathered halo). Hover follows two button types. The solid gold cta button and capacity sticker share one hover rule (SOLID GOLD BUTTONS in components.css): they grow in place to --button-hover-scale (1.04), the face lightens to --button-face-hover, and the glow brightens and spreads, all easing over --duration-slow. Both states are an even all-round dark shadow rather than an offset one, so the button lifts off the warm photograph: --button-glow-rest at rest, and --button-glow-hover on hover, darker and a little wider plus the thin gold edge the nav buttons take. There is no gold glow on these buttons; a plain gold glow blended into the brown photograph and a lightened one read as a halo. They do not lift or follow the pointer. The sticker keeps its own lightened outline ring and domed inner shading on hover. The dialog's gold close button follows the same hover in its own rule, growing with the scale property because transform already places it on the corner. Every other button takes the gold border and glow only, with no change of fill: nav links and the home button (for both hover and the current page), FAQ items open or closed, and the FAQ expand-all toggle, which also takes the nav links' faint gold ring at rest (--nav-rest-glow). The feature cards, not currently rendered, still take all three tokens and a lift. --hover-gold-fill is used by nothing else. On nav links and FAQ items the border and glow fade in and out over --duration-slow (0.45s) so they ease in gently. A tinted fill would vanish against a solid gold button, which is why those lighten their face instead. A blur alone would do nothing on these elements: the button is opaque and the cards sit on the plain ground rather than the photograph.

## Responsive

responsive.css restages the token values at each breakpoint rather than only resizing individual components, so the page recomposes at each size instead of shrinking uniformly. Each block redefines the per-area rhythm tokens, the page heading wrap width (--measure-hero) and the type sizes; component rules are limited to what a token cannot express, such as swapping the desktop nav for the burger or collapsing the feature grid to one column.

Breakpoints: 768px (tablet) and 480px (mobile). There are no height queries; the two that existed only resized the hero.


At 768px and under, page headings (h1) drop to --font-size-page-title 2.25rem (--font-size-2xl). At 480px and under: side padding is --container-padding-mobile (1.5rem, the same as tablet); page headings (h1) drop to --font-size-page-title 2rem; anything marked `{: .hide-on-phone }` in markdown (attr_list, part of extra) is hidden (no page uses it today; the home page's one paragraph shows at every size). From 768px down the burger is pushed to the right edge with margin-left auto.

## JavaScript

Each file is self-contained, has JSDoc comments and starts with `// @ts-check`. Each runs on DOMContentLoaded and does nothing if its markup is absent, so removing a feature from the templates needs no JS change.

- dialog.js: reveals each button carrying data-dialog-open and wires it to showModal() the dialog with that id. Any [data-dialog-close] inside the dialog closes it, as does a click on the dimmed area outside it, or Escape (its cancel event is held so the closing animation can run). The dialog grows out of the centre of the button that opened it and shrinks back into it on close, using the Web Animations API on the dialog and its ::backdrop, timed by --duration-dialog and --ease-dialog; with reduced motion requested it opens and closes instantly. Padding sits on .dialog__body rather than the dialog, so a click whose target is the dialog element itself can only be outside the content. The buttons ship with the hidden attribute so a visitor without JavaScript never sees one; .capacity-button[hidden] restores display: none, which the button's own display: grid would otherwise override.
- header.js: adds is-scrolled to the header whenever the page is scrolled away from the very top, and removes it back at the top, so the floating header takes its heavier surface over running text. See Header above.
- faq.js: reveals the .faq-toggle-all button and wires it to open or close every question at once, re-syncing its label when a visitor opens one by hand. It also moves the control row from its place in faq.html to directly above .faq-list, so any text before a page's first ## heading (the About page's opening paragraphs) sits above the button and visibly outside its reach. The row only exists for JavaScript visitors, so the move costs a no-JS visitor nothing. The accordions themselves are native details elements and work without it.
- menu.js: toggles the mobile menu (button.menu-toggle and nav#mobile-menu), closes on Escape, returns focus.
- reveal.js: adds is-visible to elements with class reveal as they scroll into view. Does nothing when the visitor prefers reduced motion or the browser lacks IntersectionObserver; the CSS keeps those elements visible.

## Tests

    python3 -m pytest tests

Covers front matter validation, site.json validation, H1 lifting, the FAQ transform (including the class names the stylesheet targets), root-relative rewriting, sitemap contents and the leftover-syntax check. Tests build their own tiny site in a temporary folder and do not depend on the real content.

## Deploy

.github/workflows/pages.yml runs on every push to main: installs the Python named in .python-version, installs requirements.txt, runs build.py and publishes _site to GitHub Pages through the actions/upload-pages-artifact and actions/deploy-pages actions. The repo's Pages setting must be "GitHub Actions", not "deploy from a branch". A failed build leaves the previous deploy live.

The custom domain (fairhavenwealth.co.nz) is held in the repo's Pages settings, not in a CNAME file; with Actions-based publishing GitHub ignores any CNAME file in the output. GitHub Pages serves the root 404.html for unknown paths automatically. There is no redirect mechanism on GitHub Pages: a renamed page needs a stub page at the old address with a meta refresh to the new one.

## Known limitations

- No file watcher in preview.py; rerun it after edits.
- Text before an faq page's first ## heading stays as ordinary, always-visible text, but it cannot carry a ## heading of its own, because every ## becomes a question. A heading there would have to be a ### directly under the page's h1, which skips a heading level.
- .prose img carries no box-shadow. A shadow follows the image's rectangle, not its visible pixels, so the round cut-out headshot on the About page showed a faint square card behind it.
- footer_links is read with site.get() in the footer template, so leaving the key out works. map and footer_note still need the null workaround below.
- content/site.json sets map and footer_note to null rather than omitting them. Both are documented as optional, but the templates test them with {% if site.map %} against a plain dict under StrictUndefined, so an absent key raises rather than reading as falsy and the build fails. Setting the key to null is the workaround. This is inherited from Quickie and is a defect there, not here; if it is fixed upstream, the two null entries can go.
- The dark palette is hand-set rather than derived from the BRAND block, so a brand change moves the light base layer and leaves the dark surfaces where they are. See Dark only.
- A page with show_map set loads a Google Maps iframe on view, so Google is contacted on that page whether or not the visitor looks at the map. This replaced a click-to-load facade, which avoided the request but put a control between the visitor and the one thing a contact page exists to show. The embed stays opt-in per page to keep the cost off pages that do not need it.
- Nothing checks that a class the stylesheet targets is actually present in the built page. faq_transform.py once emitted bare details elements while every FAQ rule targeted .faq-item, so the accordion fell back to browser defaults and the build still passed. A unit test now guards that specific contract, but the general gap remains: the markup hooks documented as contracts in components.css are enforced only by whichever tests happen to assert them.
- Feature card icons come from a fixed set in templates/partials/icons.html, named from a page's frontmatter. Adding an icon means editing that template, which is a step a non-technical owner will not take unaided.
- Fonts load from Google Fonts. Self-hosting would remove the external request; it is a per-site choice.
